# frontend/src/components/files

> Local file browser with an Ant Design tree, full CRUD operations, content search, diff comparison, and a FS watcher integration.

## Responsibility

`FileBrowser` renders a tree view of the local export directory. It supports lazy
directory expansion, **inline rename and inline file/folder creation** (both edited
directly in the tree — no dialog), content search, diff
comparison, reveal-in-file-manager, clipboard copy of file paths (absolute **and**
project-root-relative), **multi-select** (Cmd/Ctrl+click toggle, Shift+click range),
an **internal cut/copy/paste clipboard** (move via `RenameFile`, copy via `CopyFile`,
auto-resolving name conflicts), and **bulk** delete / cut / copy / git stage / unstage /
discard across the selection. When the `fileWatcher` feature flag is enabled it starts a
backend FS watcher and incrementally refreshes only the changed directory node on
`fs:changed` events.

**Root-level creation** is reachable without an existing folder: right-clicking the
**header title area** (top-left) or the **empty area** of the panel opens a minimal root
context menu (New Folder…, New File…, Paste) targeting the **workspace root**. It
deliberately omits destructive actions on the root directory itself. (No toolbar buttons —
the header row is icon-dense already.)

**Inline creation** (issue #874, VS Code behavior — replaces the former name modal): both
creation actions insert an **editable placeholder row into the tree** under the target
directory instead of opening a dialog. See "Inline creation" under *Patterns & integration*
for how it works.

The header also carries a **folder-switch button** (open-folder icon) whose dropdown offers
**Open Folder…** (native directory picker → `gitStore.pickExportDir`), **Open Folder in New
Window…** (`gitStore.openInNewWindow` → `OpenFolderInNewInstance` IPC — spawns a second Thaw
instance rooted at the folder), a **Recent** list of the last working directories
(`gitStore.recentDirs` → `openFolder`), and **Clear Recent**. This is the discoverable,
always-visible way to change the operating folder without opening Git Operations; the same
**Open Folder…** action is bound to **File → Open Folder…** (`⌘⇧O`) and **Open Folder in New
Window…** to its File-menu twin.

The header is laid out in **two rows** so a narrow sidebar never crushes the folder name:
row 1 is the folder title (caret + name) plus the action strip (paste, folder-switch,
search, refresh); row 2 is a dedicated **git status row** — a branch pill (with ↑ahead)
and a changed-file count pill, each opening Git Operations — shown only in a repo, where
the branch name finally has room to display in full. The standalone Git Operations icon
survives on row 1 **only for non-repo folders** (a repo's entry point is the row-2 pills),
so the action strip stays uncluttered in the common repo case.

The **git surface is folded into this panel** (there is no separate Git panel): the tree itself is
**color-coded by git status**. The `gitOverlay` memo builds its color map from the status's
**uncapped `changedPaths`** map (so the whole tree is covered even in huge change sets) and
matches it to absolute tree node keys via `relOf` — an **exact** export-dir prefix strip
(suffix matching was rejected: in large repos files that merely share a basename would
false-match). Files get a sigil + status color; folders take the color of the most
significant change beneath them (A/U both count as "new"/green, so an all-new folder stays
green rather than reading as modified). The capped
`staged`/`unstaged` lists drive the precise Stage/Unstage context menu. The full
staged/unstaged control lives in the Git Operations dialog. `FileBrowser` also owns calling
`gitStore.loadConfig()` and refreshing git status on first mount (idempotent), since the
former Git panel used to do that.

`platformUtil.ts` is a shared utility that resolves and caches the host OS string for
platform-specific labels.

## Files

| File | Purpose |
|---|---|
| `FileBrowser.tsx` | Main file browser component. Renders an Ant Design `Tree` with lazy `onLoadData` directory expansion. Implements tree-level helpers: `entriesToNodes`, `mergeNodes` (preserves expanded children), `updateNode`, `removeNode`, `renameTreeNode` / `reKeyChildren`, and `listChildrenInto` (list a directory and merge it in, marking it loaded). The dirs-first inserts `insertSorted` / `addChild` live in `fileTreeUtils.ts`. Expansion is **controlled** (`expandedKeys` + `onExpand`) so inline creation can open the target directory programmatically. `InlineNameInput` is the in-tree name editor shared by rename and creation; both editors are driven by `pendingRename` / `pendingCreate` plus an `InlineEditSession` ref. **Git status overlay**: `gitOverlay` maps the repo-relative `gitStore.status` paths onto absolute tree keys to color-code changed files (VS Code sigil colors via `sigilColor`, with a trailing status letter) and emphasize directories containing nested changes. Context menu per node: Open in editor tab, Copy path, **Copy Relative Path** (relative to `exportDir`), **Cut / Copy / Paste** (internal clipboard — see below), Rename (inline `InlineNameInput` with Enter/Escape), **Compare with last commit** (tracked changed files — diffs working tree vs HEAD via `GitGetHeadFileContent` + `queryStore.openDiff`), **Stage / Unstage / Discard changes** (changed files only), **Discard all changes (reset to last commit)** (repo-wide `git reset --hard`, shown whenever the repo has changes), New File, New Folder, Duplicate, Delete, Reveal in Finder, Diff with another file. **Multi-select**: `selKeys`/`anchorKey` state; Cmd/Ctrl+click toggles a node, Shift+click selects the range between the anchor and the click across the **visible** order (read from the DOM via `data-fbkey` on each rendered title — `visibleKeysInOrder()` — so it honors collapse state, and stays a DOM read even though expansion is now controlled). Right-clicking a node inside a multi-selection shows bulk variants (Cut/Copy/Delete/Stage/Unstage/Discard *N* items); right-clicking outside it collapses the selection to that node. **Internal clipboard** (`clipboard` state, never touches the OS text clipboard): Cut marks paths for move and dims them until pasted; Copy marks them for duplication; Paste appears on folder context menus and a header toolbar button when the clipboard is non-empty. Paste lists the target dir, resolves name conflicts (`_copy`, `_copy_2`, …) via `uniqueDstPath`, then moves (`RenameFile`, with a cross-volume `CopyFile`+delete fallback) or copies (`CopyFile`); open tabs are re-pointed via `remapTabsForMove`. **Preview tabs (#849, VS Code style):** a single click on a file (`onSelect`) opens it in the reusable *preview* tab via `openFileInTab(path, previewTabsEnabled)`; a **double-click** promotes it to a permanent tab. rc-tree has no double-click prop, so `onTreeDoubleClick` is bound on the tree wrapper and recovers the node key from the `data-fbkey` attribute (set in `titleRender`). Because rc-tree fires `onSelect` on *every* click (both clicks of a double-click) and the native `dblclick` fires on top, one open-and-pin gesture could otherwise trigger up to three concurrent `ReadFile`s for one file; two refs coalesce this — `openingPathsRef` skips a same-path open already in flight, and `pendingPromoteRef` lets a double-click that lands before the open resolves record its promote intent so `onSelect` promotes the tab (`queryStore.promoteTab`) once it exists, instead of firing its own extra read. When the tab already exists, `onTreeDoubleClick` promotes it directly. `onTreeDoubleClick` ignores modifier double-clicks (Cmd/Ctrl/Shift) — those are selection gestures that `onSelect` returns early for without opening, so recording a promote intent would leave an orphaned `pendingPromoteRef` entry that would later silently pin an unrelated plain open of the same file. Search-result clicks open as preview too. The behavior is gated on `editorTabPrefsStore.previewTabsEnabled` (Editor Preferences toggle); when off, opens go straight to permanent tabs. Inline search mode (`SearchFiles` IPC) shows grouped match results with highlighted snippets. FS watcher: the `StartFileWatcher`/`StopFileWatcher` lifecycle lives in `QueryPage` (always mounted, so ⌘B-hiding the sidebar doesn't stop it); `FileBrowser` only *consumes* `fs:changed` events (gated by the `fileWatcher` flag) to refresh the affected directory node, and suppresses self-change flicker via a `selfChangedDirs` Set with 500 ms timeout — populated by its own mutations and by editor saves (`thaw:file-saved` carries the saved path, so the watcher's echo of our own write doesn't trigger a redundant re-list). |
| `fileTreeUtils.ts` | Pure, unit-tested helpers shared by the tree code: the reserved placeholder key (`NEW_ITEM_KEY_PREFIX`, `newItemKey`, `isNewItemKey`), `insertSorted` (dirs-first alphabetical insert) and `addChild` (the same insert into a named parent — **no-ops on a never-listed parent**, see Gotchas), `findNode` / `childrenOf` (sibling lookup, `null` parent = workspace root), `insertPlaceholder` (render-time injection of the inline-creation row), `hasSiblingNamed` (case-insensitive — macOS/Windows filesystems are), `hasExtension` / `finalNewName` (any file type is creatable: the typed extension is kept, only a bare stem gets `DEFAULT_FILE_EXT` = `.sql`), and the validators: `validateRawName` (empty / path separators / Windows-invalid characters / `.` / `..` / trailing dot / `isReservedDeviceName` — `CON`, `nul.sql`, `LPT1.txt`, …) plus `validateNewName` and `validateRenameName` layered on top of it. Also `InlineEditSession` + `activeEditSession` — the identity-based guard both inline editors use to tell one edit session from the next (see Inline edit sessions below). |
| `fileTreeUtils.test.ts` | Vitest coverage for the above — placeholder insertion position, reserved-key filtering, duplicate detection, name validation. |
| `platformUtil.ts` | Module-level singleton cache for the host OS string (fetched once via `GetPlatformOS` IPC, retried on failure). Exports `getPlatformOS()` (async, caching), `getCachedPlatformOS()` (synchronous, nullable), and `revealLabel(os)` ("Reveal in Finder" / "Show in Explorer" / "Show in File Manager"). Eagerly fetches on module load. |

## Patterns & integration

- **IPC**: `ListDirectory`, `ReadFile`, `SearchFiles`, `RevealInFinder`, `DeleteFile`, `DeleteDirectory`, `RenameFile`, `CopyFile`, `CreateDirectory`, `CreateFile`, `DuplicateFile`, `GetPlatformOS` — all from `wailsjs/go/app/App`. (`StartFileWatcher`/`StopFileWatcher` now live in `QueryPage`.)
- **Events**: subscribes to `fs:changed` Wails events (`EventsOn`); payload is `{ dir: string }`. On receipt, calls `ListDirectory(dir)` and calls `mergeNodes` on the affected subtree to preserve expanded state.
- **Live git colors**: a debounced `scheduleGitRefresh` (400 ms) re-runs `gitStore.refreshStatus()` so the tree's status colors update without a manual refresh. It fires on the `thaw:file-saved` DOM event (dispatched by `queryStore.markSaved` after every editor save — watcher-independent; its `detail.path` also marks the saved dir self-changed so the watcher echo skips the re-list) and at the top of the `fs:changed` handler (covering external edits and the app's own file ops, even when the tree update is self-change-suppressed).
- **Stores**: reads `gitStore.exportDir` (directory root) and `gitStore.status` (for the git-status overlay), plus `gitStore.stageFile`/`unstageFile`/`discardFile` actions; `queryStore` (to open files as new SQL tabs), `diffStore` (to queue files for DDL diff), `featureFlagsStore` (to gate FS watcher).
- **Feature flag**: `fileWatcher` flag gates the `fs:changed` event listener here (and the watcher lifecycle in `QueryPage`). When the flag is off, the tree is still functional but does not auto-refresh on external changes.
- **Empty-directory safety** (issue #875): every `ListDirectory` result is treated as possibly `null` (`entries ?? []`, and `entriesToNodes` accepts `null | undefined`) — a nil Go slice crosses the bridge as JSON `null`. And every `entriesToNodes(...)` call is evaluated **before** the surrounding `setTreeData(...)` updater, never inside it, because React runs updaters during the render phase where a throw unmounts the whole React tree instead of reaching the enclosing `catch`. In `refresh()`, `entries: null` in a child result means the listing *failed* (stale subtree is kept); a directory that listed fine but is empty comes through as `[]` so its stale children are cleared.
- **Root-load failure state**: `rootError` records a failed root listing. `loaded` stays `false` on failure, so without it the auto-load effect re-invoked `loadRoot()` on every render (an endless `ListDirectory` loop against an unreadable folder). The panel shows a "Could not read this folder." message with a **Retry** button (clearing `rootError` re-arms the auto-load effect), and the header Reload button stays available in that state.
- **Inline creation** (issue #874): `startNewItem(kind, dir)` sets `pendingCreate` (`{ kind, parent, value }`) instead of opening a modal, and the placeholder row is injected in the **`treeForRender` memo — never into `treeData`**. Keeping `treeData` a pure mirror of the filesystem means `mergeNodes`, `refresh()` and the `fs:changed` watcher need no knowledge of the placeholder and can never wipe or duplicate it mid-edit. Its key is the reserved `^@new:<parentDir>` (see `isNewItemKey`); every real key is an absolute path, so the two can't collide. Mechanics:
  - **Reserved-key blindness**: the placeholder title carries **no `data-fbkey`**, so it's invisible to `visibleKeysInOrder()` / Shift+range; the node is `selectable: false` and `onSelect` / `onRightClick` return early for it. It's also `isLeaf: true` even for a folder — a switcher on a path that doesn't exist yet would offer to expand (and lazily list) it.
  - **Position**: `insertPlaceholder` uses the same dirs-first comparator as `insertSorted`, with an **empty title** so the row keeps a stable position instead of jumping around as the user types. A root-level create inserts into the top-level list (the workspace root is not itself a node — `childrenOf(..., null)`).
  - **Controlled expansion**: the tree switched from rc-tree's uncontrolled lazy expansion to controlled `expandedKeys` + `onExpand`, so `startNewItem` can expand the target directory. rc-tree fires `loadData` **only** for a user-driven expand, so `startNewItem` also runs the `ListDirectory` + `updateNode` listing itself when the parent isn't in `loadedKeys` (and pushes the key into `loadedKeys` so rc-tree doesn't re-list). `expandedKeys` is pruned on delete and re-keyed on rename alongside `loadedKeys`.
  - **Validation**: `validateNewName` runs on every keystroke against the parent's loaded siblings and renders under the input (`InlineNameInput`'s `error` prop). The message is **portaled to `<body>`** and positioned against the input's viewport rect (flipping above the field when it would run off the bottom of the window) — see Gotchas. It's UX polish — the backend's `O_EXCL` create (`internal/filesystem/fs.go`) remains the safety net, and an unloaded parent simply yields no siblings to compare against. **Rename shares the rules** via `validateRenameName` (same `validateRawName` core, minus the `.sql` default, and a duplicate check that ignores a case-only rename of the node itself), so the two editors can't disagree about what's typeable — rename used to silently strip path separators and throw the typed name away on an invalid character.
  - **Cancel during an in-flight create**: Escape can land while `CreateFile`/`CreateDirectory` is awaiting, past `submitCreate`'s entry guard. The item exists on disk by then and can't be un-created, so the node is still inserted (an invisible file would be a worse lie, especially with the fs watcher off) — but everything the user was cancelling is skipped: the success toast, the selection move, and the editor tab auto-open. The `catch` path bails silently too. See **Inline edit sessions** below for how the completion knows.
  - **Naming**: the action is **New File…**, not "New SQL File…" — any file type can be created. `finalNewName` keeps whatever extension was typed (`schema.yml`, `README.md`, a `.gitignore`-style dotfile) and appends `DEFAULT_FILE_EXT` (`.sql`) only to a bare stem, so the common single-word case still lands as SQL. A trailing dot is rejected rather than quietly becoming `report..sql`. The duplicate check runs against the **resolved** name.
  - **Submit / cancel**: Enter creates (`CreateFile` / `CreateDirectory` → `markSelfChanged` → order behind the eager listing, see Gotchas → insert the real node via `insertSorted`/`addChild`); a **file** then opens through `openFileInTab(path, previewTabsEnabled)`. Escape cancels with no IPC. Blur mirrors the rename editor — submit what was typed, drop the row when it's empty or invalid. A failed create keeps the input open for correction.
- **Inline edit sessions**: rename and creation are the same machine over different state, and both guard their async work with an `InlineEditSession` (`{ id, phase }`) rather than a status enum. Opening an editor mints a session, stamps its `id` into the state that editor owns (`pendingRename` / `pendingCreate`) and parks it in `renameSessionRef` / `createSessionRef`; `activeEditSession(live, captured)` is the entry guard for every submit/blur handler, and a completion resuming after its `await` compares its captured session against the ref **by identity**. That makes "cancelled" (`null`) and "superseded by a newer editor" (a different object) both read correctly. A plain `"idle" | "submitting" | "cancelled"` ref could not: opening the next editor has to reset it to `"idle"`, which silently re-arms every stale closure from the previous one — cancel a create, immediately start another, and the first one's completion would clobber the second's editor, fire its own toast and open its file. `phase` carries the Enter→blur double-submit guard within a session, and a failed submit drops back to `"editing"` so the editor can be retried.
- **Self-change suppression**: mutations performed by `FileBrowser` itself (create, rename, delete, duplicate) — and editor saves, via the `thaw:file-saved` path — record the parent directory in `selfChangedDirs` for 500 ms; incoming `fs:changed` events for those directories are ignored during that window. The key is normalized through `suppressKey` (strips a leading `/private` on macOS auto-symlink roots) so a canonical dialog-save path matches the watcher's pre-resolution `evt.dir`.

## Gotchas

- `mergeNodes` preserves existing `children` arrays only for nodes that are still directories. If an external tool replaces a directory with a file of the same name, stale children are dropped.
- Watcher is stopped (`StopFileWatcher`) on component unmount and whenever `exportDir` changes to a new value; a new watcher is started after the old one is stopped.
- `addChild` **silently drops the child** when the parent node has no `children` array yet (never listed) — seeding it with just that node would render the directory as if it held nothing else, and `onLoadData` skips a node that already has children, so the real siblings would never be fetched. Normally the node appears on expansion instead; `submitCreate` is the one caller that can't rely on that (see the next entry).
- **`submitCreate` is ordered behind `startNewItem`'s eager listing** via `session.listing` (the promise from `listChildrenInto(parent)`, stored **on the `InlineEditSession`** — see below for why not a ref). They are two independent async flows and *either* interleaving loses the new node: submit first and `addChild` no-ops on a parent that still has no children array; listing first but resolving after the insert and `updateNode`'s merge maps over a **pre-creation** snapshot, dropping the node that was just added. Neither self-heals — `onLoadData` early-returns for a parent that now has children, so collapse/re-expand won't re-fetch, and the watcher's echo is swallowed by the 500 ms self-change suppression — so the item stays invisible until a manual Reload. If the listing *failed*, the promise resolves `false` and `submitCreate` re-lists the parent instead of calling `addChild`; the fresh listing carries the item, which is already on disk. Any new "insert a node the user just created" path needs the same treatment.
- **`session.listing` hangs off the session, not a component ref**, for the same reason `id` does. A single ref is one slot that the *next* editor resets: cancel a create in a slow-to-list directory `A`, immediately start one in an already-loaded `B`, and when `A`'s `CreateFile` finally resolves it reads `B`'s (empty) slot, concludes `A` was listed, and `addChild` silently drops the node — the exact "invisible until manual Reload" failure the ordering exists to prevent. The trailing session-identity check doesn't save it: that only suppresses the toast and tab-open, long after the tree insert used the wrong signal. Reached through the session object `activeEditSession` already validated, the mismatch can't occur. Any future per-create async state belongs on the session too.
- `listChildrenInto` **drops its result when the directory is gone** (`findNode(treeDataRef.current, dir)`). A listing can still be in flight when its directory is deleted — deletion takes a confirm dialog plus an IPC, so the listing lands well after. `updateNode` already no-ops for a missing key, but `setLoadedKeys` would write back the entry the delete just pruned, and a same-named directory created later would then count as already loaded and render empty.
- `renameTreeNode` recursively re-keys all descendants so that the tree keys (which equal file paths) remain correct after a parent directory is renamed.
- Shift+range relies on `data-fbkey` being present on **every** rendered node title; `titleRender` wraps all (non-editing) nodes in a `<span data-fbkey>`. Nodes scrolled out of the DOM are not in `visibleKeysInOrder()`, so a range whose anchor is off-screen falls back to a single selection.
- The internal clipboard is local component state (not a store) and is cleared when `exportDir` changes; Cut is one-shot (cleared after a successful paste), Copy persists. After paste, `refresh()` rebuilds affected directories rather than surgically inserting nodes.
- Expansion is **controlled**: any code path that removes or re-keys nodes (delete, rename) must update `expandedKeys` as well as `loadedKeys`, or a stale key keeps a vanished directory "expanded". Programmatic expansion does **not** trigger rc-tree's `loadData` — list the directory yourself (as `startNewItem` does).
- Only **one inline editor** can be open at a time: `startNewItem` calls `cancelRename()` and `handleRenameStart` calls `cancelCreate()`, which retire the other's session as well as clearing its state. Never clear `pendingRename`/`pendingCreate` directly — a session left live in its ref would let a stale completion act on it.
- **Deleting an editor's subject retires it too**: `handleDeleteConfirm` calls `retireEditorsIn(paths)` — cancelling a `pendingRename` on a doomed path (or under one) and a `pendingCreate` whose `parent` is a doomed directory or a descendant — **before** `modal.confirm`, not after the unlink. Otherwise the editor's row vanishes with the node while its session stays live, and a late blur would `RenameFile` a path that no longer exists and toast "Rename failed: …" instead of closing quietly; worse, the confirm modal stealing focus *is* that blur, so the rename would commit and move the file out from under the delete. Running it synchronously in the click handler (rather than in `onOk`) is also what keeps it reading current `pendingRename`/`pendingCreate` state instead of a stale closure. `onRightClick` also refuses to open a context menu on the row whose own rename editor is open (mirroring the placeholder guard), so Delete can't be aimed at a node mid-edit in the first place; `InlineNameInput` stops `contextmenu` propagation so a right-click *inside* the field still gets the native paste menu.
- The inline **validation message is portaled to `<body>`** with `position: fixed`, not absolutely positioned under the input. The `<Tree>` wrapper is `overflow: hidden` (drag-selection artifacts) and auto-sizes to its rows, so an in-row message under the *last visible* row was clipped away entirely — a `z-index` can't fix clipping. `InlineNameInput` re-measures the anchor on every render plus on capture-phase `scroll` and `resize`, bailing out when the rect is unchanged (the every-render measure would otherwise loop). `pointerEvents: none` keeps the floating box from eating tree clicks.
- Work that must happen regardless of cancellation (the rename's tree/tab re-pointing, the create's node insert) goes **before** the session identity check; only the user-facing follow-up (toasts, closing the editor, opening a tab) goes after it. The disk change already happened either way.
- The "Directory is empty." placeholder and the `<Tree>` render gate on **`treeForRender.length`**, not `treeData.length` — a root-level create in an empty folder has nothing but the placeholder row to show.
